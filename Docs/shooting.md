[Slide 1] 데이터베이스 & 상태 관리 (DB & Business Logic)
--------------------------------------------------------------------------------
1. '내가 지원한 업무' 영역 부재 및 완료/취소 후 재지원 불가 문제
  * 문제: '내가 지원한 업무' 영역이 없어 대기 상태 관리가 안 되고, 완료/취소 후 다른 업무 지원이나 재지원이 막히는 현상 발생
  * 원인:
    - 지원 후 채택 결과를 기다리는 대기 상태를 확인할 수 있는 독립적인 관리 UI 부재
    - 이전 지원 이력이 DB에 남아있을 때 Supabase (task_id, member_id) 복합 유니크 제약(UQ)으로 새 INSERT 시 중복 키 에러 발생
  * 해결:
    - '나의 업무' 카드 내에 [내가 지원한 업무] 영역을 복원하여 대기 상태 확인 및 지원 취소 기능 제공
    - 지원 시 기존 이력이 있으면 중복 INSERT 대신 UPDATE로 상태를 APPLIED로 갱신하는 멱등성 로직 적용

2. 지원 취소/매칭 취소 시 목록 잔존 및 상태 불일치
  * 문제: 지원 취소 후에도 비교 목록에 남아있거나, 매칭 취소 시 재모집 불가
  * 원인: 조회 쿼리의 상태 필터링 부재 및 작업자 매칭 해제 로직 미연동
  * 해결: `status != CANCELLED` 쿼리 필터링 적용 + 매칭 취소 시 `task.unassignWorker()`로 모집 중(`OPEN`) 자동 복구

3. 모집 기한 만료 업무의 자동 상태 전이 및 예약 재화 환불 누락
  * 문제: 모집 기한(`deadlineAt`)이 지난 미매칭 업무가 계속 `OPEN` 상태로 목록에 노출되고, 의뢰자의 시간 재화(품)가 묶여 자동 환불되지 않는 문제
  * 원인: 비동기 스케줄러가 없는 환경에서 마감 기한 도래 시점의 상태 갱신 및 결제 환불 라이프사이클 처리 누락
  * 해결: 업무 목록 조회 및 대시보드 진입 시 `expireOverdueOpenTasks()` 트리거를 실행하여 만료 업무를 일괄 취소(`CANCELLED`)하고 `timeLedgerService.refundTaskReservation`을 연동해 예약금 자동 환불 및 첨부파일 정리

  * 원인: 템플릿별로 상단 [내 업무] 링크가 `/tasks/{id}/progress` 또는 `/?view=dashboard`로 상이하게 바인딩되어 라우팅 혼선 발생
  * 해결:
    - 모든 화면(`index`, `profile`, `task-progress`, `chat`)의 상단 [내 업무] 링크를 `/?view=dashboard`로 완전 통일

[Slide 5] 실시간 채팅 & 비동기 인터랙션 (Chat & Interaction)
--------------------------------------------------------------------------------
1. 채팅방 이미지 비동기 로딩 시 최하단 스크롤 위치 어긋남 현상
  * 문제: 이미지가 포함된 메시지가 있는 채팅방 진입 시 스크롤이 최신 메시지(최하단)까지 내려가지 않고 중간에 멈추는 현상
  * 원인: DOM 렌더링 시점에 이미지 리소스가 아직 로드되지 않아 높이 0으로 계산된 채 `scrollTop = scrollHeight`가 실행된 후 이미지가 뒤늦게 렌더링되면서 스크롤 위치가 위로 밀림
  * 해결: `requestAnimationFrame` 적용 및 미완료 이미지(`!img.complete`)의 `load` 이벤트 발생 시점에 최하단 스크롤을 재실행하도록 이벤트 리스너 등록, CSS `overscroll-behavior: contain` 및 이미지 최대 높이 가드로 레이아웃 안정화

2. 보낸 메시지의 읽음 여부(Read Status) 오판정 문제
  * 문제: 내가 보낸 메시지가 상대방의 실제 채팅방 열람 여부와 무관하게 항상 '읽음'으로 처리되는 문제
  * 원인: 메시지 뷰 변환 시 `mine || message.getReadAt() != null` 조건으로 인해 내가 보낸 메시지(`mine=true`)가 무조건 true로 평가됨
  * 해결: `mine` 조건을 분리하고 오직 상대방의 `message.getReadAt() != null` 여부로만 읽음 상태를 판별하도록 수정하여 정확한 수신 확인(1 표시) 기능 제공

3. 매칭 완료 업무의 채팅방 미생성 시 500/404 에러 방지 (ChatRoom Dynamic Creation)
  * 문제: 업무 매칭 완료 후 채팅 버튼 클릭 시 기존 데이터나 예외 상황으로 인해 채팅방이 DB에 생성되지 않은 경우 `NoSuchElementException` 에러 발생
  * 원인: 매칭 트랜잭션과 채팅방 생성 간의 결합도 및 데이터 정합성 누락에 따른 `chatRoomRepository.findByTaskId()` empty 반환
  * 해결: `findRoomIdForTask()` 호출 시 방이 없으면 매칭된 의뢰자-작업자 정보를 기반으로 채팅방을 동적으로 자동 생성(`getOrCreate`)하여 안전한 채팅방 진입 보장

2. 결과 파일 용량 초과 예외 처리
--------------------------------------------------------------------------------
  [문제]
  * 6MB를 초과하는 결과 파일을 전송하면 Tomcat multipart 요청 제한에서 먼저 차단되어
    `413 Content Too Large` Whitelabel Error Page가 노출됨.

  [처리 내용]
  * 결과 파일 선택 시 브라우저에서 6MB 초과 여부를 즉시 검사.
  * 초과 파일은 선택을 해제하고
    "첨부 파일 용량이 너무 커서 전송할 수 없습니다. 6MB 이하 파일을 선택해주세요."
    안내를 표시.
  * 큰 파일 선택 후 제출 버튼을 눌러도 전송을 막아 현재 결과 제출 화면을 유지.
  * 브라우저 검사를 우회한 요청도 `MultipartException`을 처리하여 같은 진행 화면으로
    리다이렉트하고 동일한 안내 문구를 표시.

  [사용자 동작]
  * 큰 파일 때문에 작성 화면을 잃거나 서버 오류 페이지로 이동하지 않음.
  * 보안 정책상 파일은 다시 선택해야 하지만, 화면과 오류 안내는 유지됨.

1. AI 초안 기능에서 "AI 기능이 활성화되지 않았습니다"가 표시되는 문제
--------------------------------------------------------------------------------
  [증상]
  * 업무 등록 화면에서 AI 초안 생성을 요청하면
    "AI 기능이 활성화되지 않았습니다. 직접 입력해주세요." 안내가 표시되고,
    `/tasks/ai/draft` 요청이 503 응답으로 끝남.

  [원인]
  * Google AI 프로필은 활성화되어 있었지만, `AiChatClientConfiguration`의
    `@ConditionalOnBean(ChatModel.class)` 조건이 Google AI 자동 구성보다 먼저 평가될 수 있었음.
  * 그 결과 `ChatClient.Builder` 빈이 등록되지 않아 AI 기능이 비활성 상태로 판단됨.

  [해결]
  * `ai-google` 프로필 전용 설정에서 조건부 빈 등록을 제거함.
  * `ChatModel`을 `chatClientBuilder` 메서드의 인자로 직접 주입하여,
    Google AI 모델이 구성된 뒤 `ChatClient.Builder`가 항상 생성되도록 수정함.
  * 실행 프로필에 `ai-google`과 API 키 설정이 포함되어 있는지 확인한 뒤 애플리케이션을 재시작함.

  [검증 및 예방]
  * `ApplicationTests` 통과 및 `web`, `db`, `ai-google` 프로필 활성화를 확인함.
  * 자동 구성 빈에 대해 초기 평가 순서 영향을 받을 수 있는 조건부 등록은 피하고,
    프로필별 설정과 생성자/메서드 주입으로 의존성을 명확히 유지함.

2. "Port 8080 was already in use"로 애플리케이션이 실행되지 않는 문제
--------------------------------------------------------------------------------
  [증상]
  * IntelliJ 또는 Gradle로 실행할 때 웹 서버가 시작되지 않고
    `Web server failed to start. Port 8080 was already in use.` 메시지가 출력됨.

  [원인]
  * 이미 Gradle `bootRun`으로 실행 중인 애플리케이션이 8080 포트를 사용 중인데,
    IntelliJ에서 같은 포트로 애플리케이션을 한 번 더 실행하려 했음.

  [해결]
  * `Get-NetTCPConnection -LocalPort 8080 -State Listen`으로 해당 포트를 점유한 프로세스를 확인함.
  * 확인한 프로세스만 종료한 뒤, 8080 포트가 비어 있는 것을 확인하고 IntelliJ 실행을 다시 시도함.

  [예방]
  * 개발 중에는 IntelliJ 실행과 Gradle `bootRun` 중 하나만 사용함.
  * 동시에 여러 인스턴스가 필요하면 실행 환경별로 `SERVER_PORT`를 다르게 지정함.
